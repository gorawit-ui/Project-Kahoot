# 45-player rehearsal — 21 October 2026

**Decision: NOT YET APPROVED for the live event.** Forty-five players could rejoin and submit in this bounded rehearsal, but the first join burst had one error and measured request latency is too high to certify the current client timeout behavior. Continuous gameplay, real devices and the latest deployed fixes still require testing.

## Environment and method

- Public production API: `https://jixgo-magical-24.vercel.app`, application commit `241c7a2` (the existing production build, not the stability PR).
- Real Supabase backend. One uniquely marked synthetic quiz, 20 synthetic questions and a dedicated QA room; no event question or event room was changed.
- Forty-five independent player cookies. A barrier released 45 HTTP requests together per stage, with a 25-second HTTP timeout. These are protocol clients, not 45 browsers.
- One burst for each stage, not sustained 45-player polling for a full game. Host state was advanced through scoped administrative SQL for the synthetic room; production Host-login UI was not used.
- Source and raw sanitized measurements: `scripts/load-event.py` and `qa/load-results-20261021.json`. Session cookies stayed in ignored temporary files.

This does not test cleared cookies, incognito mode, a different phone, actual mobile network loss or browser background suspension.

## Findings and prepared changes

1. **Join-response loss can strand an identity.** Previously the server created a player and only then issued the cookie. If that response was lost, retrying could have no cookie for the already occupied nickname. The stability branch now establishes an opaque httpOnly session before Join, preserves it on retry and allows 15 seconds for Join. Local API tests confirm cookie reuse; a component test verifies retry sequencing. Awaiting deployment and real browser verification.
2. **Session lookup scales with the room's player count.** Existing RPCs compare bcrypt against multiple rows in the room. An actual Supabase invalid-token lookup across the 45-player fixture averaged 170.023 ms over three calls. Repeated state polling therefore has a measurable authentication cost.
3. **Prepared lookup optimization is NOT applied.** `20261021153202_index_player_session_lookup.sql` adds a private indexed SHA-256 fingerprint for lookup while retaining the existing bcrypt check. New joins populate the fingerprint; existing sessions populate it after successful legacy verification. Existing bcrypt hashes/cookies are retained.

Automatic approval review rejected applying item 3 to the live database because it replaces four core authentication/readiness/summary/answer RPC definitions and has a broad production impact without specific live-change approval. No alternative path was used to execute it. A follow-up catalog query confirmed the new column is absent on Supabase.

## Isolated validation of the pending database change

`npm run test:db` uses PGlite with pgcrypto and no Supabase connection. It validates:

- 45 legacy players rejoin with the same player IDs, and all original bcrypt hashes remain unchanged.
- A matching fingerprint alone is rejected when the bcrypt check fails.
- New players receive a lookup fingerprint, and client table/helper access remains denied.
- The 20-question/two-player gameplay regression still passes under service_role, including duplicate prevention, deadlines, stale question IDs, scoring and Q20 results.
- The prepared rollback restores original RPCs, removes the new lookup column, and retains returning-player access.

In that isolated WASM runtime, the same valid-player summary lookup averaged 266.09 ms before the change and 7.78 ms after it (three samples per measurement). These are relative local measurements, **not** a live 45-user concurrency benchmark. Raw local results: `qa/lookup-local-validation-20261021.json`.

Additional local checks: 13/13 client component tests, 47/47 API/session validation cases, TypeScript and the production build passed. Rollback SQL is prepared in `qa/index-player-session-lookup-rollback.sql`; it has not been run on production.
